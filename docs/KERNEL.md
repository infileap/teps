# 微内核边界

**约束（项目所有者原话）：**

> 「内核可能必须控制在微小级别，否则不易升级维护。」

本文档把这句话变成一条**判据**，而不是一个愿望。

---

## 一、先纠正度量：不是行数，是**状态量**

直觉会说"微小 = 行数少"。**那是错的。**

> **决定"不易升级维护"的不是代码行数，是内核持有的可变状态量。**

理由：升级内核的痛点几乎全在**迁移状态**。一个 500 行的内核如果抱着 50 个可变字段，
比 8000 行无状态代码难维护得多。行数只是状态的**代理量**，而且是个会骗人的代理量。

**⇒ 微小化的正道是让内核接近无状态：**

```
内核接近无状态  ⇒  升级 = 换二进制 + 重放日志  ⇒  "不易升级维护"被根治
```

**这不是新机制，是这个系统本来就要有的性质**：权威状态在盘上，不在进程里。
重启是一个受支持的操作，不是一次故障。

---

## 二、进内核的判据

> **只有"必须唯一权威、必须原子、必须每次经过"三种性质，配得上进内核。**

一切其他东西——无论它多重要、多中心、多想当然——都是 `organs/` 里的一个外设。

**这条判据的可操作性在于它是否可以回答"否"。** 大多数想进内核的东西，
被问"它是纯函数吗"时会立刻露馅。

---

## 三、内核里的四个概念

| 概念 | 靠哪条性质进来 | 它持有状态吗 |
|---|---|---|
| **Frame** | 每次经过 | ❌ 无状态 |
| **Log** | 唯一权威 | ⚠️ 状态在**盘上**，不在内存 |
| **Budget** | 原子 | ⚠️ 内存只是缓存，日志是真相 |
| **Refusal** | 每次经过 | ❌ 无状态常量表 |

**注意这张表里唯一需要一点内存状态的是 Budget**——
而它必须留在内核里的理由，**正好就是"必须原子"**（否则超支竞态）。
判据在起作用，不是人在分配。

### 为什么 `Log` 不算"持有状态"

因为**进程不持有它**。日志在盘上；进程重启后重放它。
内核的内存里没有一棵"当前状态树"需要被迁移——**那是升级成本的来源，而它不在内核里。**

### P0 落地：四概念对应的类型

| 概念 | 类型 | 文件 |
|---|---|---|
| Frame | `Frame` + `ParseFrame` / `Marshal` / `Canonical` | `core/frame.go` |
| Refusal | `Refusal` + 13 个拒绝码常量（每个自带可重试答案） | `core/refusal.go` |
| Log | `Log` / `Entry` + `Open` / `Append` / `Replay` | `core/log.go` |
| Budget | `Budget` / `Account` | `core/budget.go` |

公开类型共 **6** 个（Gate 3 上限 12），456 行（Gate 1 上限 3000）。
`Account` 是唯一持有可变值之物——理由正是"检查与扣减必须不可分割"。

**追加的顺序是被刻意排定的**：先落盘并 `Sync`，**成功之后**位置才前移。
若落盘失败，位置绝不声称记录已经存在。这条顺序就是"失败语义也是契约"在代码里的样子。

## 四、出核清单（每条都是一次有理由的驱逐）

| 被驱逐 | 为什么它不配 |
|---|---|
| 仲裁器（opex + capex） | 输入是状态快照，输出是决策。**纯函数。** |
| 上下文合成器 | 挑候选、打分、填预算。**纯函数。** |
| **核验器** | 按 `verify.assert` 独立判定 outcome。**纯函数。** |
| 记忆 / 索引 | 可重算。丢了能重建。 |
| 技能店 | 文件系统 + 协议。 |
| 算力池注册表 | 一张表。 |
| HTTP 传输 | **进程，不是盘上格式。** |
| 脚本宿主监督 | 超时与熔断策略。 |
| 停滞计数器 stall/repeat/waste | 观测，不是权威。 |

**"纯函数"是这条清单的统一理由。**
纯函数意味着：同样的输入给同样的输出，不需要唯一权威、不需要原子、不需要每次经过。
所以它们不需要进内核——**这不是妥协，这正是它们该待的地方。**

---

## 五、一处修正：内核不管真实性

设计早期写过一句：

> ~~"链管完整性（integrity），内核管真实性（validity）"~~

**按"内核必须微小"的约束，后半句必须改掉：**

> **链管完整性；真实性交给外设里的核验器。内核谁都不管。**

理由是机械的：**内核不认识"技能""策略""增益"**（它被 Gate 4 禁止认识这些词），
所以它**不可能**判定"这次执行是否真的成功了"。

早先想把真实性放进内核，是想让它更"重"、更权威。
**"微小"约束暴露了那是错的**：权威不等于能干，**唯一权威 ≠ 什么都由它判断。**

## 六、四条守卫（可跑，已验）

```sh
python3 tools/check_kernel.py            # 跑四条守卫
python3 tools/check_kernel.py --strict   # 内核尚未声明四个概念即判失败（CI 用）
```

| # | 守卫 | 阈值 | 为什么守这个 |
|---|---|---|---|
| 1 | 源码行数（非空，不含 `_test.go`） | ≤ 3000 | 状态的代理量 |
| 2 | Go 直接依赖（`require` **和** `replace`） | = 0 | 供应链纪律 |
| 3 | 公开类型 | ≤ 12 | 概念数量的代理量 |
| 4 | ★ 领域词 / 宿主词 | = 0 | **病因** |

### 第 4 条为什么最强

> **行数超标是症状，领域词泄漏是病因。**

如果"技能""策略""增益"出现在内核源文件里，说明**外设的职责漏进来了**——
那比行数超了严重得多，**而且出现得更早**。

它一条 grep 同时守住两件事：
1. **内核只说自己的话**（不认识宿主）；
2. **内核保持微小**（不认识上层领域）。

### 它是怎么做到的（一个不显然的实现细节）

**天真的子串匹配守不住这一条。** `\bskill\b` 看不见 `skillRef`；
`\bgain\b` 看不见 `TotalGain`。

所以守卫先把文本切成**子词**（保留 camelCase 边界），再对子词做**前缀**匹配：

```
TotalGain   → total, gain     → gain 命中
skillRef    → skill, ref      → skill 命中
bargain     → bargain         → 不命中（正确的假阳性控制）
against     → against         → 不命中
escalation  → escalation      → escalat 命中
```

**这不是纸上推演，是注入测试过的**：往 `core/` 里放一个
`type skillRef struct{ TotalGain int }`，守卫报 `2 处`、exit 1；
同一文件里的对照行 `bargain against explain` 不报。

⚠️ **守卫扫描 `.go` 源文件，不扫 `.md`。** 所以 `core/README.md` 可以自由写出
被禁的词来解释禁令，而 `core/doc.go` 不能。**注释里出现这些词同样算泄漏**——
这不是疏漏，是有意的：文档说明禁令，代码服从禁令。

## 七、升级语义

按上面的结构，升级内核是一次**可逆的、低风险的操作**：

```
换二进制 → 重放日志 → 校验提交锚
```

- **没有状态迁移**：进程本来就不持有权威状态；
- **可回滚**：换回旧二进制，日志还是那条日志；
- **可验证**：提交锚（`state_hash` 与链的对齐）能立刻发现不一致。

**这正是"微小"想要的东西——不是代码好看，是升级不痛。**
